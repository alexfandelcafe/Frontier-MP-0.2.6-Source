5. PROBLEMA ACTUAL DE RUNTIME
============================================================

La red y el proceso básico funcionan:

- Frontier DLL carga.
- Bootstrap IPC funciona.
- RDR abre.
- Cliente conecta.
- Se reciben snapshots.
- GameThreadDispatcher funciona.
- Native invoker funciona parcialmente.
- worldLoaded puede llegar a 1.
- stableWorldLoaded puede llegar a 1.
- local player sigue sin existir.
- GET_PLAYER_ACTOR(-1) devuelve 0.
- La escena 3D puede regresar al mundo/frontend sin gameplay local.

Ejemplos observados:
connected as player 1
serverTick=384
snapshot players=2 remoteEntities=1

y continúa durante cientos de ticks.

Pero:
worldLoaded=1
stableWorldLoaded=1
localPlayer=0
GET_PLAYER_ACTOR(-1)=0

Conclusión:
Networking/snapshots no eran el cuello de botella.
El cuello de botella es el lifecycle de creación/asociación del local player dentro de RAGE.

NO tratar:
STREAMING_IS_WORLD_LOADED=1
como equivalente a gameplay/player-ready.

## 64. CEF pump ownership + D3D12 queue discovery follow-up (2026-09-27)

Los logs de ejecución después del cambio al Present detour histórico muestran:
- `CefInitialize thread=7604`
- la primera excepción `0xC0000005` ocurre en `FrontierClient.dll` desde el hilo 5468
- el fallo aparece mientras el Present histórico está activo y antes de que exista una cola D3D12 resuelta para el swapchain real.

La lectura más probable del fallo es un uso cruzado del pump CEF: `CefOverlay::on_present()` ejecutaba `CefDoMessageLoopWork()` desde el hilo que entra por `Present`, que no necesariamente es el mismo hilo que inicializó CEF. El código fue corregido para que:
1. `CefInitialize` registre `GetCurrentThreadId()` como `cefThreadId`.
2. `pump_on_game_thread()` compruebe que el dispatcher sigue ejecutándose en ese hilo y sea el único sitio que llama `CefDoMessageLoopWork()`.
3. `on_present()` no invoque CEF; solamente consume el último framebuffer OSR ya producido y, cuando existe una cola válida, ejecuta la composición D3D11On12.

Para el bridge D3D12, la búsqueda de la command queue ahora:
- conserva primero los offsets descubiertos por el swapchain de prueba histórica;
- amplía el escaneo dinámico del objeto swapchain de 0x600 a 0x4000 bytes;
- añade una segunda búsqueda sobre el objeto `ID3D12Device` para builds donde la cola no esté retenida en el objeto swapchain.

Esto no reintroduce los hooks IAT de `CreateDXGIFactory*`, ni shadow-vtables de factories/swapchains en el camino activo.

Nota técnica: la cola pasada a `D3D11On12CreateDevice` debe ser una cola 3D válida y el uso de recursos envueltos requiere coordinación con la cola D3D12 que usa el rendering/present de la aplicación. La documentación oficial de Microsoft describe el flujo con el mismo command queue para el interop. No se considera resuelto hasta comprobar en el runtime que Frontier encuentre la cola real de RDR y complete la composición sin una nueva excepción.

## 65. Eliminar el scan privado de command queue del Present (2026-09-27)

Los logs posteriores confirmaron que el crash seguía apareciendo antes de que el scan privado del swapchain pudiera producir una queue válida. Se reemplazó ese mecanismo por una captura basada en la API pública de DXGI:

- Se obtiene desde el swapchain de prueba la dirección compartida de `IDXGIFactory2::CreateSwapChainForHwnd`.
- Se instala un detour de esa implementación compartida, además del detour compartido de `Present`.
- Cuando RDR crea su swapchain D3D12, el parámetro `IUnknown* device` recibido por `CreateSwapChainForHwnd` se consulta como `ID3D12CommandQueue`. La documentación de Microsoft especifica que para D3D11On12 las command queues suministradas deben ser colas 3D, y sus ejemplos pasan la queue usada por el swapchain. citeturn694664search0turn694664search6
- Frontier guarda la queue junto con una referencia al swapchain real de RDR.
- `CefOverlay::on_present()` ya no inspecciona memoria privada de objetos COM para encontrar la queue. Si no existe una pareja `swapchain real + queue real`, no inicializa D3D11On12 ni compone CEF.

También se eliminó el fallback que podía aceptar accidentalmente la command queue del swapchain de prueba. Esto evita usar una queue de otro dispositivo/swapchain para el interop.

Commit de implementación: `fdf4fcea41163ba0c184ed0234da2b4a1c5f4052`.

antes del primer `Present` que intente inicializar D3D11On12. Si ese mensaje no aparece, el siguiente punto de diagnóstico es el target compartido de `CreateSwapChainForHwnd`, no el objeto swapchain privado.

## 66. Game-thread dispatcher/context y aislamiento del worker (2026-09-27)

Se aplicó una corrección estructural para separar el worker de las operaciones que requieren contexto vivo de RDR.

### Dispatcher
`GameThreadDispatcher::pump()` ya no acepta el primer `scrThread::Wait` como game thread automáticamente. El `Wait` debe estar asociado a un contexto de script cuyo nombre haya sido observado por `GET_SCRIPT_NAME` y que pertenezca a la whitelist:
- `content/main`
- `content/pressstart`
- variantes con separador `/` o `\\` y extensión `.sc`.

El contexto se registra por el puntero `context`, y `gameThreadId_` solo se fija cuando llega un `Wait` autorizado. Los nombres siguen registrándose incluso después del límite de trazas.

Durante detach, `wait_hook()`, `GET_THIS_SCRIPT_ID` y `GET_SCRIPT_NAME` conservan punteros fallback a sus handlers originales para que una entrada concurrente al hook no se convierta en una llamada perdida al native original.

### RdrBridge
Se añadió `require_game_thread_access()` y las operaciones que leen/modifican estado vivo del motor fallan cerradas si el hilo actual no es el game thread autorizado. Esto incluye:
- runtime game state;
- lectura del local player;
- spawn/despawn/transform/validation de actores remotos;
- locomoción;
- bootstrap histórico de LoadOnline;
- eventos UI que llaman al motor.

### ClientRuntime
El worker conserva únicamente el trabajo de red/temporización. Las operaciones de RDR pasan al dispatcher:
- `FrontierSession::update` se ejecuta en el game thread y publica un `FrontierRuntimeState` POD al worker;
- `ensure_local_player` se ejecuta en el game thread;
- `read_local_player_state` se ejecuta en el game thread, devuelve una copia POD y luego el worker la envía por red;
- `RemotePlayerManager::update/clear` se ejecutan en el game thread;
- snapshots entrantes siguen siendo datos y `RemotePlayerManager` quedó protegido contra acceso concurrente.

### Alcance
Esto corrige el problema de sincronización señalado en los puntos 1, 2, 6, 7, 9 y 10. No convierte el protocolo UDP actual en ENet ni implementa por sí solo ResourcesManager/Lua/HTTP/server-browser de RDRMP; esas partes requieren reproducir el contrato de red y los subsistemas externos correspondientes, y no se declaran compatibles hasta que ese backend exista.
